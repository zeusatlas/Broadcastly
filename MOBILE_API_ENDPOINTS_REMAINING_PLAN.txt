TITLE:
Broadcastly Mobile UI — Remaining API Integration Plan

OBJECTIVE:
Build and integrate the remaining backend endpoints required by the completed
mobile UI. Every feature should use real, authorised, validated, paginated and
server-filtered data instead of demo or local preview data.

COMMON API WORK:

- Add request and response interfaces for every endpoint.
- Add feature API modules, hooks, loading states, error states and retry flows.
- Add server-side search, filters, pagination and sorting for every large list.
- Add safe query caching with keys based on all request parameters.
- Refetch or invalidate affected lists after every successful mutation.
- Use idempotency keys for SMS, credit, import and other retry-sensitive writes.
- Keep permissions and organisation scope enforced by the API, not only by the UI.

FEATURES AND ENDPOINTS STILL NEEDED:

1. Dashboard / Home
   - Organisation overview and dashboard summary.
   - Recent broadcasts, pending approvals, notifications and credit balance.
   - Dashboard counts must come from live endpoints, not sample values.

2. Organisation
   - Organisation logo upload and removal.
   - Unit browsing with parent, search and pagination.
   - Executive appointment, end appointment, suspend and reactivate actions.
   - Member search endpoint for appointing an executive.
   - Head-position title update using the organisation's configured title.

3. Members
   - Paginated member list with server-side search and filters.
   - Member detail, create, update and deactivate endpoints.
   - Import template, upload, preview, duplicate resolution, confirmation and
     import history endpoints.
   - Import progress, summary and failure details for long-running jobs.

4. Broadcasts and Templates
   - Broadcast list, detail, create draft, update draft and delete/cancel draft.
   - Recipient selection and server-side recipient estimate.
   - Cost and segment estimate.
   - Submit for approval, approve, reject, schedule, send and cancel actions.
   - Template list, search, create, update, use and delete endpoints.
   - Idempotent send and schedule requests.

5. Approvals
   - Paginated approval queue with search and status filters.
   - Approval detail endpoint.
   - Approve and reject-with-reason actions.
   - Permission and status validation on every approval action.

6. Credits
   - Balance and paginated transaction history with period filters.
   - Credit allocation to executives or units.
   - Purchase flow and purchase status polling.
   - Allocation, purchase and adjustment idempotency protection.
   - Refresh balance and ledger after every successful credit action.

7. Reports
   - Paginated broadcast history and report detail.
   - Delivery summary and recipient-level delivery status.
   - Search, status and period filters.
   - Export endpoint and retry-failed-delivery action where supported.

8. Notifications
   - Paginated notification list with unread filter.
   - Mark one notification as read and mark all as read.
   - Unread count for the home header and refresh after read actions.

9. Settings and More
   - Current profile data from `/auth/me`.
   - Device/session list and session revocation actions.
   - Persistent notification preferences and support configuration where
     supported by the product requirements.

EXPECTED OUTCOME:
Have every completed mobile screen backed by a documented, tested and secure
API endpoint, with consistent pagination, filtering, caching, mutation refresh,
permission checks and retry-safe behaviour.

SCOPE NOTE:
SMS and payment work today covers endpoint contracts and flow wiring only.
Real provider logic and provider-specific credentials will be implemented later.

DEFINITION OF DONE:

- No required screen depends on demo data or local preview state.
- Every endpoint is registered in API documentation and has validation tests.
- Protected data is scoped in the backend query.
- Lists support pagination, search and filters where the UI provides them.
- Mutations return the shared response envelope and refresh affected data.
- API typecheck, lint and tests pass.
- Live PostgreSQL checks are completed for database-backed endpoints.
